# 10. Technical Design & Implementation

**Project:** Front Command  
**Status:** Approved technical direction  
**Purpose:** Define the technical architecture, implementation principles, project structure, and development workflow.

---

## 10.1. Основная техническая концепция

Front Command разрабатывается как браузерная стратегическая игра для ПК.

Основная цель архитектуры — создать универсальный игровой движок, который поддерживает разные театры военных действий, кампании, миссии и сценарии через данные и конфигурацию, а не через отдельные версии игрового кода.

Ключевые принципы:

1. Разделение игрового движка, интерфейса и игрового контента.
2. Модульная архитектура с чёткими границами ответственности.
3. Data-driven подход: исторические данные и настройки отделены от программной логики.
4. Возможность разрабатывать проект небольшими независимыми задачами.
5. Минимальная зависимость от конкретного ИИ-агента или среды разработки.
6. Отсутствие обязательного сервера и платной серверной инфраструктуры.
7. Проверяемость изменений и сохранение работоспособности уже созданных систем.

Архитектура должна быть достаточно строгой, чтобы разные разработчики и ИИ-агенты создавали совместимые части проекта.

При этом не следует создавать избыточную сложность ради функций, которые пока не нужны.

## 10.2. Технологический стек

Основной стек:

- **TypeScript** — игровая логика, симуляция, типы данных.
- **React** — пользовательский интерфейс.
- **Vite** — сборка и локальная среда разработки.
- **HTML/CSS** — структура и оформление интерфейса.
- **SVG / Canvas** — визуализация карты и игровых объектов.
- **JSON** — хранение игрового контента и конфигураций.
- **Zod** — проверка корректности загружаемых JSON-данных.

TypeScript обеспечивает статическую проверку типов, но не заменяет проверку реальных данных во время загрузки. Поэтому JSON необходимо валидировать через Zod.

Конкретные библиотеки для тестирования, картографической визуализации и других специализированных задач выбираются при реализации соответствующих модулей. Не следует заранее добавлять большое количество зависимостей.

## 10.3. Разделение приложения

**Игровые правила остаются в документе 03.**

Приложение должно состоять из нескольких логических уровней.

### A. Core / Engine

Основная игровая логика:

- игровой календарь и время;
- состояние кампании;
- игровые сущности;
- симуляция;
- правила и расчёты;
- обработка игровых действий;
- система событий;
- управление состоянием игры.

Core не должен зависеть от React и компонентов интерфейса.

### B. Game Systems

Отдельные игровые подсистемы:

- Combat;
- Movement;
- Logistics;
- Intelligence;
- Communication;
- Command;
- Politics;
- Economy;
- Events;
- Personnel;
- Reports;
- Save System.

Каждая система отвечает за свою область и взаимодействует с остальными через определённые интерфейсы.

### C. Data Layer

Отвечает за:

- загрузку JSON;
- проверку схем;
- регистрацию контента;
- работу с идентификаторами;
- загрузку кампаний и сценариев;
- сохранение и загрузку игровых данных.

### D. UI Layer

Отвечает за:

- главное меню;
- глобальную карту;
- штаб;
- панели управления;
- документы;
- отчёты;
- журналы;
- окна событий;
- визуальное отображение игровых систем.

UI отображает состояние игры и передаёт действия игрока игровому движку. Он не должен самостоятельно реализовывать правила симуляции.

### E. Platform Layer

Отвечает за:

- локальное хранение;
- импорт и экспорт сохранений;
- работу с браузерным окружением;
- PWA и офлайн-возможности;
- системные настройки.

## 10.5. Разделение данных и программного кода

Это один из главных архитектурных принципов Front Command.

Исторический контент и настройки не должны быть жёстко прописаны в игровой логике.

Примеры данных:

- страны;
- командиры;
- дивизии;
- армии;
- фронты;
- карты;
- города;
- территории;
- события;
- исторические даты;
- сценарии;
- параметры кампаний;
- национальные особенности;
- состав и характеристики соединений.

Эти данные должны храниться отдельно от программного кода.

### Универсальный движок

Движок должен обрабатывать данные по общим правилам.

Например, добавление новой дивизии, командира или исторического события не должно требовать изменения логики движка, если соответствующие механики уже существуют.

Если для нового контента нужна новая механика, она сначала реализуется как самостоятельная универсальная система. После этого её можно использовать в нужных кампаниях через конфигурацию.

Не допускается создание множества отдельных реализаций одной и той же механики для разных кампаний.

Не следует создавать в движке специальные ветвления для конкретных исторических кампаний без обоснованной необходимости.

## 10.6. Театры, кампании и миссии

Используется следующая структура понятий:

- **Театр военных действий** — пакет контента, например Eastern Theater или Far Eastern Theater(в будущем).
- **Кампания** — война, например Вторая мировая война.
- **Фронт** — игровая миссия внутри кампании.

Эти понятия не должны смешиваться с военной организационной структурой, где также существуют фронты, армии, корпуса и дивизии.

Каждый пакет контента использует общие форматы данных и манифесты.

Пример:

```text
content/
└── theaters/
    └── eastern-theater/
        ├── manifest.json
        │
        └── campaigns/
            └── ww2/
                ├── campaign.json
                ├── map.json
                ├── countries.json
                │
                ├── units/
                │   ├── soviet.json
                │   └── german.json
                │
                ├── commanders/
                ├── events/
                └── missions/
```

Файлы разделяются по логическому назначению и удобному размеру.

Не следует помещать всю кампанию в один огромный JSON-файл. Но и чрезмерное дробление, например отдельный файл для каждой небольшой сущности, нежелательно.

## 10.7. Формат данных и схемы

Основной формат — JSON.

Используется комбинированный подход:

- TypeScript interfaces/types описывают структуру данных в коде.
- Zod проверяет реальные JSON-объекты во время загрузки.
- JSON хранит исторический контент и конфигурации.

YAML не требуется на начальном этапе. Его можно добавить позднее, если появится конкретная практическая необходимость.

Все основные сущности должны использовать общие схемы.

Например, разные армии могут иметь разные характеристики, но используют одну структуру данных.

Для каждой важной сущности необходим уникальный постоянный ID.

Нельзя полагаться исключительно на названия или порядковые номера: названия могут изменяться, а ссылки на сущности должны оставаться стабильными.

Загрузка некорректных данных должна приводить к понятной диагностике, а не к скрытым ошибкам симуляции.

## 10.8. Взаимодействие систем

Используется комбинированная архитектура взаимодействия.

### Прямые вызовы

Применяются, когда одна система непосредственно нуждается в результате работы другой.

Например, система движения запрашивает результат расчёта доступности маршрута.

### Типизированные события

Используются для независимых реакций нескольких подсистем.

Например, после завершения боя Combat публикует событие BattleCompleted.

На него могут независимо реагировать:

- Reports;
- Intelligence;
- Logistics;
- Command;
- Journal.

Событийная система должна иметь определённые типы событий, источники, структуру данных и правила обработки.

Нельзя превращать её в хаотичный механизм, в котором системы отправляют друг другу произвольные сообщения.

### Порядок симуляции

Игровая симуляция должна иметь контролируемый порядок обновления систем.

Логика симуляции не должна зависеть от частоты кадров интерфейса.

По возможности одинаковое начальное состояние и одинаковая последовательность игровых действий должны приводить к одинаковым результатам. Это важно для тестирования, сохранений и воспроизведения ошибок.

## 10.9. Запуск и хранение данных

Игра ориентирована на ПК.

Основной формат запуска — обычный веб-сайт.

Дополнительно можно использовать PWA для установки игры и последующей работы без подключения к интернету.

Обязательный сервер не требуется.

Основные требования:

- симуляция работает на устройстве игрока;
- прогресс хранится локально;
- нет обязательной регистрации;
- нет обязательной платной серверной инфраструктуры;
- сохранения можно экспортировать и импортировать;
- игра должна по возможности работать офлайн после первоначальной загрузки необходимых ресурсов.

Для локального хранения игрового прогресса рекомендуется IndexedDB.

Экспорт и импорт сохранений рекомендуется реализовать через отдельный формат файла, содержащий необходимые данные сохранения и информацию о версии.

Размещение сайта и загрузка первоначальных файлов требуют хостинга, но это не означает необходимость постоянного игрового сервера.

## 10.10. Система сохранений и версий

Необходимо различать:

1. Версию игрового движка.
2. Версию формата сохранения.
3. Версию пакета контента или кампании.

Сохранение должно содержать информацию, необходимую для определения совместимости.

При изменении формата сохранений необходимо использовать явные последовательные миграции.

Пример:

```text
Save v1
  ↓ migration
Save v2
  ↓ migration
Save v3
```

Перед миграцией создаётся резервная копия исходного сохранения.

Миграция должна проверять результат. При ошибке оригинальное сохранение не должно уничтожаться или перезаписываться.

Необходимо стремиться к совместимости со старыми сохранениями, но не обещать бессрочную поддержку всех исторических версий.

## 10.11. Производительность

Целевой уровень — средние современные ПК с возможностью регулировать производительность и визуальные эффекты.

Принципы:

- симуляция не зависит от FPS;
- интерфейс не должен блокироваться во время расчётов;
- тяжёлые визуальные эффекты можно отключать;
- частота обновления отдельных систем может регулироваться;
- не следует выполнять лишние перерасчёты;
- сначала измерять производительность, затем оптимизировать.

Web Workers можно использовать для тяжёлых вычислений, если профилирование покажет необходимость.

WebAssembly рассматривается только в случае реального ограничения производительности, которое не удаётся устранить более простыми средствами.

Не нужно преждевременно усложнять архитектуру ради оптимизации.

## 10.12. Тестирование и контроль качества

Тестирование должно охватывать ключевые игровые системы и их взаимодействия.

### Unit tests

Проверяют отдельные функции и расчёты.

### Integration tests

Проверяют взаимодействие нескольких систем.

### Data validation tests

Проверяют корректность JSON и соответствие схемам Zod.

### Regression tests

Проверяют, что новые изменения не сломали уже работающие функции.

### Build checks

Проверяют, что приложение собирается без ошибок.

### Manual testing

Применяется для важных игровых сценариев и визуальных изменений.

Особенно важны проверки:

- боевой системы;
- потерь и результатов сражений;
- движения соединений;
- снабжения;
- сохранения и загрузки;
- миграций;
- загрузки контента;
- взаимодействия игровых систем.

Не нужно стремиться к формальному проценту покрытия тестами. Приоритет — корректность наиболее важных игровых механик.

## 10.13. Организация Git и приёмка изменений

Разработка контролируется пользователем.

Основной рабочий процесс:

1. Пользователь формулирует небольшую задачу.
2. ИИ-агент изучает нужные документы и существующий код.
3. Агент реализует только согласованную задачу.
4. Изменения передаются пользователю.
5. Пользователь проверяет и отбирает изменения.
6. При необходимости другой агент проверяет результат.
7. Если обнаружены ошибки, изменения возвращаются на исправление.
8. После успешной проверки пользователь вручную принимает изменения и загружает рабочую версию в GitHub.

Git используется для хранения проверенных состояний проекта и возможности отката.

Рекомендуется фиксировать принятые изменения отдельными понятными коммитами.

Необязательные сложные Git-процессы и автоматическое принятие изменений не требуются.

## 10.14. Архитектурные изменения

ИИ-агент не имеет права самовольно перестраивать архитектуру проекта.

Небольшие архитектурные изменения разрешены, если агент:

- объяснил необходимость;
- проверил влияние на существующий код;
- сохранил совместимость;
- обновил соответствующую документацию.

Крупные изменения требуют предварительного согласования с пользователем.

К крупным изменениям относятся:

- изменение основных архитектурных слоёв;
- изменение публичных интерфейсов между системами;
- изменение общих схем данных;
- изменение формата сохранений;
- замена ключевых технологий;
- масштабное перемещение или переписывание модулей.

Если задача требует крупного изменения, агент сначала должен объяснить проблему, предложить варианты и дождаться разрешения.

## 10.15. Критерии завершения задачи

Задача считается завершённой, когда:

1. Реализован требуемый результат.
2. Проект запускается и собирается.
3. Соответствующая функция действительно работает.
4. Не сломаны существующие системы.
5. Пройдены относящиеся к задаче тесты.
6. Изменения соответствуют архитектуре и документации.
7. При необходимости обновлены схемы, документация и тесты.
8. Проверены важные интеграции.

Для важных игровых систем требуется дополнительное ручное тестирование.

Если какой-либо пункт невозможно проверить, агент обязан прямо указать это. Нельзя заявлять об успешной проверке, если она фактически не проводилась.

## 10.16. Подход к разработке с ИИ

Front Command разрабатывается небольшими последовательными задачами.

Это обязательное практическое ограничение, учитывающее использование бесплатных ИИ-моделей с ограниченным контекстом и лимитами.

Основные правила:

- одна задача должна иметь один понятный результат;
- агенту передаются только необходимые документы и файлы;
- крупная система разбивается на независимые этапы;
- сначала создаются контракты и схемы, затем реализация;
- каждый этап должен оставлять проект в проверяемом состоянии;
- между задачами фиксируется текущее состояние разработки;
- новый агент должен иметь возможность продолжить работу без чтения всей истории предыдущих чатов.

Не следует поручать одному агенту создание всей подсистемы за один запрос.

Рекомендуемая последовательность разработки новой системы:

1. Изучение требований и существующей архитектуры.
2. Проектирование интерфейсов и схем.
3. Создание типов и контрактов.
4. Реализация базовой логики.
5. Добавление тестов.
6. Интеграция с другими системами.
7. Проверка и документация.

Эта последовательность может изменяться в зависимости от задачи, но границы ответственности должны сохраняться.

## 10.17. Документация проекта

Документация должна быть разделена на небольшие тематические файлы.

Рекомендуемая структура:

```text
docs/
├── PROJECT_MAP.md
├── STATUS.md
│
├── architecture/
│   ├── overview.md
│   ├── module-boundaries.md
│   ├── data-flow.md
│   └── event-system.md
│
├── systems/
│   ├── combat.md
│   ├── movement.md
│   ├── logistics.md
│   ├── intelligence.md
│   └── ...
│
├── data/
│   ├── schemas.md
│   ├── content-structure.md
│   └── identifiers.md
│
└── decisions/
    ├── ADR-001-technology.md
    └── ...
```

Документация обновляется вместе с соответствующими изменениями.

PROJECT_MAP.md должен оставаться короткой картой проекта, а не копией всей технической документации.

STATUS.md должен отражать фактическое состояние разработки, реализованные функции, известные проблемы и ближайшие задачи.

История обсуждений в чатах не является единственным источником истины. Утверждённые решения должны находиться в документации проекта.

## 10.18. Итоговый принцип

Front Command должен развиваться как единая модульная система, которую можно постепенно расширять.

Главная цель — не максимальная сложность архитектуры, а возможность безопасно создавать, проверять и интегрировать новые игровые механики небольшими независимыми задачами, даже если над ними работают разные ИИ-модели с ограниченным контекстом.
