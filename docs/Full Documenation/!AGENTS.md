# AGENTS.md — Front Command

## 1. Назначение проекта

Front Command — стратегическая игра о Второй мировой войне, в которой игрок выступает в роли оперативного командующего.

Проект использует TypeScript, React и Vite. Игровая логика отделена от интерфейса. Исторический контент хранится отдельно от программного кода.

Твоя задача — помогать развивать существующий проект, сохраняя его архитектуру и совместимость.

**Главное правило: не переписывай работающий проект ради выполнения отдельной задачи.**

## 2. Обязательное начало каждой задачи

Перед изменением кода:

1. Прочитай этот файл.
2. Прочитай `docs/PROJECT_MAP.md`, если он существует.
3. Прочитай только документацию, относящуюся к текущей задаче.
4. Изучи существующие файлы и похожие реализации.
5. Определи, какие модули затрагивает задача.
6. Проверь существующие типы, интерфейсы и тесты.
7. Кратко опиши план.

Не предполагай, что проект пустой или что нужная функция ещё не существует.

Если задача уже частично реализована, продолжай существующую реализацию.

## 3. Ограничение размера задачи

Работай только над поставленной задачей.

Не добавляй несвязанные функции, улучшения и рефакторинг.

Предпочитай изменения, которые:

- имеют один понятный результат;
- затрагивают минимально необходимое количество файлов;
- могут быть проверены отдельно;
- не требуют изменения всей архитектуры.

Если задача слишком большая, предложи разделить её на несколько последовательных подзадач.

Не пытайся реализовать целую крупную игровую систему одним запросом.

## 4. Работа с контекстом

Учитывай, что ИИ-агенты могут иметь ограниченное окно контекста и лимиты использования.

Поэтому:

- не читай всю документацию без необходимости;
- не копируй в ответ большие фрагменты файлов;
- сначала ищи конкретные определения и зависимости;
- используй существующие документы как источник истины;
- не пересказывай всю историю проекта в каждом ответе.

Если информации недостаточно, запроси конкретные файлы или уточнения.

Не выдумывай существующие функции, интерфейсы, типы и пути.

## 5. Архитектурные правила

1. Соблюдай разделение Core, Systems, Data, UI и Platform.
2. Не помещай игровую логику в React-компоненты.
3. Не связывай игровые системы напрямую с интерфейсом.
4. Используй существующие интерфейсы и схемы данных.
5. Не создавай дублирующие реализации.
6. Не добавляй зависимости без необходимости.
7. Не используй глобальное состояние без предусмотренного архитектурой механизма.
8. Не создавай циклические зависимости между модулями.
9. Не изменяй публичные интерфейсы систем без необходимости и согласования.
10. Соблюдай принятые соглашения об именовании и структуре файлов.

Если не знаешь, куда поместить новую функцию, сначала изучи архитектуру и существующие аналогичные решения.

## 6. Работа с игровыми данными

Исторические данные и конфигурации должны быть отделены от логики движка.

Используй JSON и существующие схемы TypeScript/Zod.

Запрещено:

- прописывать исторические составы соединений непосредственно в игровой логике;
- создавать отдельную структуру данных для каждой кампании;
- использовать названия вместо постоянных ID;
- обходить проверку данных;
- менять общие схемы без проверки зависимых файлов.

Если новая механика требует изменения схемы, сначала выясни, какие существующие данные от неё зависят.

## 7. Работа с существующим кодом

Перед изменением файла выясни:

- за что он отвечает;
- кто его использует;
- какие интерфейсы он предоставляет;
- какие тесты его покрывают.

Не переписывай файл полностью, если достаточно локального изменения.

Не удаляй существующий код только потому, что предпочитаешь другой способ реализации.

Не меняй названия и расположение файлов без необходимости.

Не исправляй посторонние ошибки в рамках несвязанной задачи, если они не мешают её выполнению. Сообщи о них отдельно.

## 8. Архитектурные изменения и разрешения

Небольшие изменения разрешены самостоятельно, если они обоснованы и не нарушают существующие контракты.

Крупные изменения требуют предварительного согласования с пользователем.

Примеры крупных изменений:

- изменение структуры основных модулей;
- изменение общих интерфейсов между системами;
- изменение основных схем данных;
- изменение формата сохранений;
- замена ключевых технологий;
- масштабное переписывание или перемещение файлов.

При необходимости такого изменения:

1. Останови реализацию соответствующей части.
2. Объясни проблему.
3. Укажи затрагиваемые модули и файлы.
4. Предложи варианты.
5. Дождись решения пользователя.

Не обходи это правило через серию формально небольших изменений, которые в совокупности меняют архитектуру.

## 9. Тестирование

После реализации:

1. Запусти относящиеся к задаче тесты.
2. Проверь TypeScript.
3. Проверь сборку проекта, если это возможно.
4. Проверь связанные системы.
5. Добавь или обнови тесты для новой логики.
6. Проверь, что изменения не нарушили существующее поведение.

Не утверждай, что тесты прошли, если ты их не запускал.

Если запуск невозможен, объясни причину и укажи, какие проверки остались.

## 10. Документация

Обновляй документацию, если изменились:

- архитектура;
- публичные интерфейсы;
- схемы данных;
- правила взаимодействия систем;
- формат сохранений;
- способы запуска и тестирования.

Не создавай новую документацию ради каждого небольшого изменения.

Поддерживай `PROJECT_MAP.md` актуальным, если изменились структура проекта или связи модулей.

## 11. Формат выполнения задачи

Работай по следующему процессу:

### Этап 1 — Inspect

Изучи релевантные файлы, документацию, зависимости и тесты.

### Этап 2 — Plan

Составь короткий план с указанием файлов, которые предполагается изменить.

### Этап 3 — Implement

Реализуй только согласованную задачу.

### Этап 4 — Verify

Запусти доступные проверки и исправь ошибки, связанные с изменением.

### Этап 5 — Report

Подготовь отчёт для пользователя.

## 12. Формат итогового отчёта

После каждой задачи обязательно сообщи:

**1. Результат**
- Что реализовано.
- Какое поведение добавлено или изменено.

**2. Изменённые файлы**
- Перечень файлов.
- Кратко, что изменилось в каждом.

**3. Проверки**
- Какие тесты запускались.
- Результаты TypeScript и сборки.
- Что проверено вручную.
- Что не удалось проверить.

**4. Архитектура**
- Изменялись ли интерфейсы или схемы.
- Есть ли новые зависимости.
- Требуется ли обновление документации.

**5. Известные проблемы**
- Незавершённые части.
- Ошибки.
- Возможные последствия.

**6. Следующий шаг**
- Только если он действительно необходим для продолжения работы.

Не заявляй о полной готовности, если остались непроверенные части.

## 13. Правила безопасности изменений

- Не удаляй файлы без необходимости.
- Не перезаписывай сохранения и пользовательские данные во время тестирования.
- Не добавляй секреты, ключи и пароли в репозиторий.
- Не изменяй настройки Git и окружения без необходимости.
- Не выполняй массовые операции без предварительной проверки их последствий.
- Не устанавливай случайные зависимости вместо изучения существующего стека.

## 15. Главное правило

Ты работаешь не над отдельным прототипом, а над частью единого проекта Front Command.

Каждое изменение должно сохранять совместимость с остальной системой.

**Не переписывай то, что уже работает. Не создавай то, что уже существует. Не меняй то, что не входит в задачу. Проверяй результат перед отчётом.**
